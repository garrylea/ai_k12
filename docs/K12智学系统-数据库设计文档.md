## 1. 设计约定

### 1.1 通用规则

| 项 | 约定 |
|----|------|
| 数据库 | MySQL 9.7.1 LTS |
| 命名 | 全部 `snake_case`；表名为复数名词 |
| 主键 | `BIGINT AUTO_INCREMENT`，列名 `id`；API 层对外暴露时使用前缀 ID（如 `stu_xxx`、`dlg_xxx`） |
| 时间戳 | `created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)`、`updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)`，所有表均包含 |
| 软删除 | 需要审计/恢复的表使用 `deleted_at DATETIME(3)`；仅 `parents`、`students`、`ai_dialogues`、`ai_messages`、`orders`、`subscriptions`、`rewards` |
| 枚举 | 使用 `VARCHAR` + 应用层校验，不使用 MySQL ENUM 类型（便于后续迁移） |
| 外键 | 所有 FK 显式声明，指定 `ON DELETE` 行为 |
| 索引命名 | `idx_{表名}_{列名}`；唯一索引 `uniq_{表名}_{列名}` |
| TEXT | 用于问题选项、卡片元数据、管控配置、报告内容等可变结构（存 JSON 字符串，应用层解析） |
| JSON | **允许使用 MySQL 原生 JSON 类型**（2026-09-15 起，首个用例 `chinese_passages.key_terms` / `sentences`，见 §3.14；2026-09-17 增 `sentence_meanings`）。**mysql2/promise 读取时已自动 parse**——Row 上直接是对象/数组，应用层**不要再 `JSON.parse`**（见 `apps/server/src/database/repositories/chinese-passages.repo.ts`）。既有表继续沿用上行的 TEXT 存 JSON 字符串（那一类仍需应用层解析），**不做存量迁移**——两种存法并存，新表用原生 JSON |

### 1.2 updated_at 的自动维护（列级 `ON UPDATE`，**不用触发器**）

```sql
updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
```

**所有带 `updated_at` 的表都用这一个写法**：`DEFAULT` 负责插入时填值，`ON UPDATE` 负责行被 UPDATE 时自动刷新。

**不要再建 `BEFORE UPDATE` 触发器来维护 `updated_at`。** 历史上 28 张表走触发器、另有 2 张表（`admins` / `student_hidden_questions`）两种机制都没有；2026-09-19 已全部统一为列级写法，原因：

- 触发器是**独立对象**，`schema.sql` 与既有库不同步时会**静默缺失**。实测 dev 库 `information_schema.TRIGGERS` 里 28 条只装了 1 条，且那条长在**已废弃**的 `aux_error_books` 上——于是 27 张在用的表 `updated_at` 在行被 UPDATE 时**根本不刷新**，不报错、极难发现。
- 列级写法随 `CREATE TABLE` / `ALTER TABLE ... MODIFY COLUMN` 走，不存在「忘了装」。

迁移见 `tools/db/migrations/2026-09-19_updated_at_on_update.sql`（30 张表 `MODIFY COLUMN` + 删除 28 条历史触发器，幂等）。`schema.sql` §15 只留一行说明，**勿再加 `*_updated_at` 触发器**。

| updated_at | DATETIME(3) | NO | CURRENT_TIMESTAMP(3) | |

`content_metadata` TEXT 结构：
```json
{
  "images": [{"url": "oss/xxx.png", "alt": "图1", "position": "after"}],
  "layout_hint": "two_column",
  "override_scroll": "allow",
  "intro": "解方程：",
  "questions": [{"n": 1, "text": "2x + 3 = 7，求 x"}],
  "needs_fallback": false
}
```

字段说明：

| 字段 | 适用 card_type | 说明 |
|------|---------------|------|
| `images` | 全部 | 插图列表，`{url, alt, position}` |
| `layout_hint` | 全部 | 布局提示，如 `two_column` |
| `override_scroll` | 全部 | `allow` / `disable`，覆盖 `card_type` 默认滚动策略。不设则按 `card_type` 默认值 |
| `intro` | `practice` | 题前说明（可选），如"解方程：" |
| `questions` | `practice` | `[{n: 题号, text: 题面原文}]`。由 data-refinery 抽取并经子串校验通过后才写入；校验失败（题面不在卡片正文中）则丢弃并置 `needs_fallback=true` |
| `needs_fallback` | `practice` | bool。`true` 表示 LLM 抽题校验失败或无有效题，前端走正则兜底从 `content` 中切题；`false` 表示 `questions` 可用 |

> **practice 卡 `questions` 与判题端点**：`/api/practice/judge` 请求体的 `questionText` 取自 `content_metadata.questions[].text`。data-refinery `db_loader.build_content_metadata` 在入库阶段对每条 question 做子串校验（`question_text_valid`），无效题面丢弃并置 `needs_fallback=true`，避免前端渲染不存在的题。`backfill_practice_questions.py` 为已入库的历史 practice 卡补标。

##### 卡片类型分类法（card_type）

| card_type | 适用学科 | 内容语义 | 默认滚动策略 | 典型来源 |
|-----------|---------|---------|------------|---------|
| `concept` | 数学/理科 | 概念引入、情境导入、定义 | 禁用（超长则二次拆分） | 主题图、情境图、概念定义段 |
| `example` | 数学/理科 | 例题（含解题步骤 + 紧跟的"做一做"） | 禁用（超长则二次拆分） | 例1/例2 + 紧跟做一做 |
| `practice` | 数学/理科 | 综合练习题集 | 允许（题量学生自控） | 课时末"练习N"、节末"习题" |
| `explore` | 数学/理科 | 思考、探究、实验拓展 | 允许小幅滚动 | 想一想、思考、探究、阅读与思考 |
| `summary` | 数学/理科 | 小结、归纳 | 禁用 | 课时/单元小结 |
| `reading` | 语文/英语 | 整课阅读内容 | 允许 | 一整课课文 |

**滚动条策略规则**：默认值由 `card_type` 决定（见上表）。前端读取 `card_type` 即可决定是否显示滚动条，无需逐卡配置。个别卡片可通过 `content_metadata.override_scroll` 覆盖默认值，例如某道综合例题特别长时可设 `"override_scroll": "allow"`，避免强行二次拆分破坏解题连贯性。

**知识点关联**：`knowledge_point_ids[]` 将"卡片"（展示单元）与"知识点"（语义标签）解耦——一张 `example` 卡通常映射 1 个知识点，一张 `practice` 卡可能映射多个知识点（综合练习），一张 `reading` 卡映射该课涉及的全部知识点。

##### 卡片切分规则

切分在内容导入时执行，产出 `cards` 行。人教版数学教材本身已按知识点编排（每个例题/教学活动对应一个知识点，"做一做"紧跟例题），因此按教材自然标题块切分即可，规则识别为主，AI 仅在超长块二次拆分时介入。

**小学数学切分规则**：

| 教材标题块 | 产出卡片 | 说明 |
|-----------|---------|------|
| 主题图/情境导入 | 1 张 `concept` | 含跨页情境图 |
| 例N + 紧跟的"做一做" | 1 张 `example` | 做一做不单独成卡，它是例题的即时巩固 |
| "想一想"/"思考" | 1 张 `explore` | 穿插的探究活动 |
| 课时末"练习N" | 1 张 `practice` | 综合应用题集 |
| 单元"小结" | 1 张 `summary` | 单元级归纳 |

**初中数学切分规则**：

| 教材标题块 | 产出卡片 | 说明 |
|-----------|---------|------|
| "思考"/"探究" | 1 张 `explore` | 概念引入前的探究 |
| 例N + 紧跟"练习" | 1 张 `example` | 节内例题+即时练习 |
| 节末"习题"/"复习巩固" | 1 张 `practice` | 综合题集 |
| "阅读与思考"/"实验与探究" | 1 张 `explore` | 拓展栏目 |
| 章末"小结" | 1 张 `summary` | 章级归纳 |

**语文切分规则**：

| 教材内容 | 产出卡片 | 说明 |
|---------|---------|------|
| 一整课（课文+字词+赏析） | 1 张 `reading` | 语文不做细拆，整课单卡带滚动 |

**超长块二次拆分规则（AI 后备）**：当 `concept`/`example`/`summary` 卡内容预估超一屏（启发式：渲染后高度 > 视口 1.2 倍，或纯文本 > 800 字且含多步骤）时触发：

- `example` 超长：按解题步骤拆，"题面+分析"为卡1，"解题步骤"为卡2，`sort_order` 连续递增，`card_type` 保持 `example`，`title` 加"(续)"后缀。
- `concept` 超长：按段落拆，`card_type` 保持 `concept`。
- 二次拆分由 AI 辅助判断切点，但 `card_type` 与 `lesson_id` 不变；拆分产出的多张卡共享同一组 `knowledge_point_ids`。

MVP 仅实现 `prerequisite` + `contains` 两种关系。递归 CTE 查询示例：
```sql
WITH RECURSIVE prereqs AS (
  SELECT dst_id, src_id, 1 AS depth
  FROM knowledge_relations
  WHERE dst_id = :target_id AND relation_type = 'prerequisite'
  UNION ALL
  SELECT kr.dst_id, kr.src_id, p.depth + 1
  FROM knowledge_relations kr
  JOIN prereqs p ON kr.dst_id = p.src_id
  WHERE kr.relation_type = 'prerequisite' AND p.depth < 5
)
SELECT * FROM prereqs;
```

**材料字段使用说明**：
- 短材料（几百字）：直接存 `material_text`
- 长材料/音频/视频：存 `material_url`，指向素材目录（见 §9）

**辅轨答疑题目入库与去重**：
- 辅轨答疑中学生提出的每一道具体题目（有题干需作答者），由 AI 结构化为 题干/题型/知识点/难度/答案+解析 后入库此表（`source` 标 `auxiliary`），同时进入 `main_error_books`（`source=auxiliary`，不参与清零门禁，PRD §6.2/§7.10/§7.4）。
- **去重**：题干规范化后计算 `content_hash`，与已有题等值比对（走 `uniq_q_content_hash` 唯一索引）。命中则复用已有 `question_id`，未命中则新题入库。hash 精确匹配为主，未命中时辅以限制范围（同学科+题型）的文本相似度兜底。UNIQUE 约束在并发写入时兜底，`QuestionsRepository.findOrCreate` 捕获 `ER_DUP_ENTRY` 后回退为复用。
- **质量校验**：结构化后做轻校验（题干完整、题型合法、有可解答案）；不通过的题仅入 `main_error_books` 供复习（question_id 为 NULL），不入此表以免污染组卷。
- 入库题可作为单元检测/期中/期末组卷素材（PRD §7.6）。

1. **家长端按学科配置**（`PUT /api/parent/students/:id/subject-configs/:subjectId`）：家长选 年级+册别+版本 后 create-or-update 本行（未开始学习时 `status='not_started'`，不落 current_unit/lesson 指针）。某学科已开始学习（`status≠not_started` 或 `current_lesson_id` 非空）且版本/册别变化时，**重置学习状态**：current_unit/lesson/card_sort 置 NULL、status 回 `not_started`、时间戳清空；历史错题（`main_error_books`）与作业记录保留在库但不再展示/不再阻塞清零门禁（门禁查询按 `progress.textbook_version_id` 过滤，见 main_error_books 节）。
2. **首次学习自动初始化**（`updateProgress`）：无 progress 行时按学生所在课的 semester 反写本行。

无 progress 行时的**默认版本推导规则**（星链图回退 + 家长配置页预选）：同学段（`textbook_versions.grade_band` = 学生 school_level 或所选年级学段）候选中 **edition 非空优先（新课程标准修订版），再按 id 降序（后入库=更新）**；册别按学生年级（`students.grade` → `grade_N`）匹配 `semesters.grade`，无匹配退 sort_order 最小。

状态转换规则：
```
not_started → in_progress  (首次打开课程)
in_progress → in_progress  (一课完毕，进入下一课)
in_progress → unit_test    (单元最后一课完成且错题清零)
unit_test  → in_progress  (单元检测通过且错题清零，进入下一单元)
in_progress → midterm      (到达期中分界点)
in_progress → final        (学期所有单元完成)
in_progress → semester_complete (期末通过且清零)
```

##### 主线学习查询路径

内容层级表（`subjects → textbook_versions → semesters → units → lessons → cards`）在主线学习中**从不被串联 JOIN**。以"学生登录 → 选课 → 数学星链图 → 点星球 → 点小节 → 上课"主场景为准：

| 页面 | 查询 | 查询数 | JOIN 数 |
|------|------|--------|---------|
| 选课页 | `subjects WHERE is_active` + `progress WHERE student_id` | 2 | 0 |
| 星链图 | `progress WHERE student_id+subject_id` + `units WHERE semester_id` | 2 | 0 |
| 小节列表 | `lessons WHERE unit_id` | 1 | 0 |
| 卡片学习 | `cards WHERE lesson_id`（含面包屑时 +2 JOIN：lessons、units，整个列表只算一次） | 1 | 0~2 |
| 卡片翻页 | 前端本地翻页（`TextbookCard.onPrev/onNext`） | 0 | 0 |

**关键结论**：

- 主线热路径是"按父 ID 查子列表"的单表查询，父 ID 来自上一页或 `progress` 指针。6 层层级表从不被串联 JOIN，层级数 ≠ JOIN 数。
- `progress` 表是**单指针状态机**（`uniq_progress_student_subject`，每生每科一行），星链图的三态（已完成/当前/锁定）从指针推导：
  - `unit.sort_order < current_unit.sort_order` → 已完成
  - `=` → 当前
  - `>` → 锁定
- 不需要 `lesson_progress` 表（每生每课一行）来支撑三态展示；该表仅在需要"完成度 % / 用时 / 最后访问时间"等细粒度时才引入。
- 唯一需要 JOIN 的点是卡片头面包屑（`第2单元 › 第3课`），且整个卡片列表只算一次，不是每张卡算一次。卡片列表接口 URL 已含 `unitId`/`lessonId`，服务端按主键查 2 行即可拼出。

**为何不合并层级**：每层都绑着一个功能边界——`subjects`（学科选择）、`textbook_versions`（版本选择）、`semesters`（期末考试 scope）、`units`（单元检测边界，`assessments.scope_unit_ids`）、`lessons`（作业边界，`homeworks` 1:1 lessons）、`cards`（学习/展示单元）。合并任何一层都会丢失对应的功能语义。

- **Unique: `uniq_goals_student_scope_metric` ON `(student_id, scope_subject_id, metric)`** —— 「按 `(学科, 指标)` upsert」的前提（`ON DUPLICATE KEY UPDATE`）。2026-09-20 起目标改为**按学科**，`(student_id, metric)` 不再成立（同一个 metric 会在多个学科各有一行）
- **为什么要有生成列（2026-09-20 实测，勿改回）**：MySQL 的唯一索引**把 NULL 视为互不相等**，直接用 `UNIQUE (student_id, subject_id, metric)` 时 `subject_id IS NULL` 的行会**失去唯一性** → `ON DUPLICATE KEY UPDATE` 静默不命中、同一个目标被反复插入。故用生成列把 NULL 折成 0；而 `metric IS NULL` 的历史停用行仍留 NULL（否则多行 `(student_id, 0, NULL)` 会互相冲突，`ADD UNIQUE KEY` 直接失败）。

- **口径**：`period` / `title` **不是家长可填字段，而是由 `metric` 派生**（`daily_*` → `daily`，`weekly_*` → `weekly`）。落地时由服务端按 `metric` 写死，避免同一目标出现两种写法
- **`reminder_enabled` 恒 0**：提醒本期不做（2026-09-20 用户裁决；本仓无调度器、无短信通道），列保留待后续立项

- Index: `idx_chinese_passages_filter` ON `(grade_band, semester, sort_order)` —— 按册次筛 + 按序排
- **抽题池（三个专项口径各不相同，有意为之，勿「统一」）**：
  - **默写** = `verified=1 AND memorize_required=1 AND is_active=1`
  - **解释** = `verified=1 AND is_active=1 AND JSON_LENGTH(sentences) > 0`
    —— 不设 `memorize_required`（「要背诵」不是「要理解翻译」的必要条件），
    另加「内容就绪」闸门（没切过句的篇目点进去没题目）
  - **含义（2026-09-17）** = `verified=1 AND is_active=1 AND JSON_LENGTH(sentences) > 0 AND sentence_meanings IS NOT NULL`

- 入库幂等：按业务键先查后 `UPDATE` / `INSERT`，`ON DUPLICATE KEY UPDATE` **不含** `verified` / `memorize_required` / `is_active`（否则管线重跑会刷掉人工标定）。解释三列由 `interpretation_cli` **只 UPDATE 这三列**，语句里不出现任何状态位
- **不用 `content_hash` 去重**：该列服务于 `questions`，本表以业务键为身份
- 判定路径（按 `passage_id` 取单篇）**有意不设闸门**——见 spec §6 的守卫适用范围说明

### 3.15 埋点与账本（Phase 0，2026-09-20）

> **实施状态**：**已于 2026-09-20 实施**（迁移 `tools/db/migrations/2026-09-20_analytics_ledger.sql`；两表同时进 `tools/db/schema.sql`）。采集侧改动见 API 设计文档 §6.26 与 `docs/ai-core-changelog.md` 同日条目。
> 背景：`ai_messages` 的 model/token 四列**生产恒写 NULL**、`ModelClient` 默认流式且 `aggregateStream()` 曾把 usage 硬编码 `{0,0,0}`，导致「次数 / token」两样都算不出。本批补齐**存储 + 采集**。
> 设计见 `docs/superpowers/specs/2026-09-19-analytics-instrumentation-design.md` §4.5/§4.6/§6.2/§6.3/§6.5/§6.6，实施计划 `docs/superpowers/plans/2026-09-19-analytics-instrumentation-phase0.md`。
> **口径（用户 2026-09-19 裁决）**：**本期只记 token 数，不记价格与成本** —— 两表**都没有** `cost` 或价格快照列，`llm_models` 也不加价格列。以后按 token 计价，钱由 token 换算。早期误加的 `cost` + 两个价格快照列（`llm_call_logs`）与两个价格列（`llm_models`）已由同迁移用带存在性守卫的 `DROP COLUMN` 收敛掉——留着 `cost` 会恒为 0，而 0 表示「真免费」，会误导后续查成本的人。

| browser | VARCHAR(20) | YES | NULL | `chrome` / `safari` / `edge` / `firefox` / `electron` / `other`（**服务端**解析 UA） |
| screen_class | VARCHAR(20) | YES | NULL | `ipad_landscape` / `desktop` / `tablet_portrait` / `mobile`（**前端**上报） |
| input_type | VARCHAR(10) | YES | NULL | `touch` / `mouse` / `hybrid`（**前端**上报） |
| app_shell | VARCHAR(10) | YES | NULL | `web` / `electron`（**前端**上报） |

- PK: `id`
- FK: `fk_ss_student_id` ON `student_id` → `students(id)` **ON DELETE CASCADE**（会话是学生产生的数据，随学生删除；与账本表的 `SET NULL` 口径不同——账本是审计数据）
- Index: `uniq_ss_uid(session_uid)`、`idx_ss_student_time(student_id, started_at)`（家长端单人窗口查询）、`idx_ss_student_module(student_id, module, started_at)`、`idx_ss_open(status, last_heartbeat_at)`（`closeStale` 惰性收尾）、`idx_ss_platform_time(platform_class, started_at)`（Phase 2 设备分布）
- **不分区**：MySQL 要求分区键出现在**每个唯一键**（含主键）里，给本表分区会逼我们放弃 `uniq_ss_uid`；清理改用 `DELETE ... WHERE created_at < ?` 的定时任务（spec §11）

**三条口径（勿「统一」掉）**：

1. **`active_seconds` 只由服务端累计、单次封顶 45s**：心跳 / 结束时按 `last_heartbeat_at → NOW(3)` 的秒数差值增量，且只在**上一状态为 visible** 时计（hidden 暂停）。**客户端上报的秒数一律不采信**。不封顶时，用户关掉标签 2 小时后若有一次迟到心跳，差值会把整段 2 小时算成学习时长；封顶后最坏只多算 45s。`GREATEST(0, ...)` 顺带兜住客户端 / DB 时钟回拨。
2. **设备画像只到「类别」**：**不存**任何能唯一定位一台设备的标识，**也不存原始 UA 字符串**。`platform_class` / `browser` 由服务端从 `User-Agent` 粗分类（防客户端伪造），`screen_class` / `input_type` / `app_shell` 由前端上报（服务端拿不到），**非法值落 NULL 且不报错**（设备信息是尽力而为）。设备维度的**报表**属运营面（Phase 2），不进家长端。
3. **iPad 校正**：iPadOS 13+ 的 Safari UA 写的是 `Macintosh`，只看 UA **必然**把 iPad 判成 Mac——而 iPad 横屏正是本产品的主断点。服务端在写入时应用「`platform_class == 'mac'` 且 `input_type == 'touch'` → `ipad`」校正。

**挂机四列（2026-09-20 加，P6.6/P6.9）三条补充口径**：

- **`hidden_*_seconds` 不参与学习时长**：家长端学习时长口径（`parent-analytics.repo.ts` 的 `EFFECTIVE_SESSION`）只看 `active_seconds`，新增四列**不改既有口径**。
- **⚠️ `UPDATE ... SET` 的列顺序是承重的**：MySQL 单表 `SET` **从左到右求值、读到的是已更新后的值**，所以两个累计列必须排在 `client_state = ?` 与 `hidden_reason = ?` **之前**（它们要读旧值）。新增行不得打乱既有 `active_seconds` 那段的顺序，有专门的顺序回归测试钉着。
- **阈值判定只在两处发生**：心跳时 + `end` 时（覆盖「最小化后直接关页面」）。⚠️ **无 `end` 的会话（浏览器崩溃 / 被强杀 / 断电）不做判定** → 走神预警永不产生（已知限制，见 API 文档 §6.28）。另外 `hidden_reason` 在极少数情况会贴错标签：先因 `idle` 变 hidden、随后标签页又被切走时，状态机在 `hidden` 下对 `HIDDEN` 是空操作、该段仍记为 `idle`。

- **无 `ref_id` 外键（重要）**：`ref_id` 指向 `chinese_passages.id` / `english_words.id`，但那两张内容表会**全量重灌**；设入向外键会让重灌被卡死。同 `student_word_progress.word_id` 的既有教训

**三条口径（勿「统一」掉）**

3. **`is_correct` 与 `error_counted` 是两件事**：前者是「判对判错」，后者是「是否计错」。`off_target`（答成常见义，学生答的没错）、`unanswered`（显式点「不认识」）、`undetermined`（判题失败）三者 **`is_correct` 为 NULL 且 `error_counted = 0`**。

### 6.2 归档策略

- `ai_messages`：超过 12 个月的已归档会话消息，迁移至归档表或冷存储
- `devices`：过期会话定期清理（每日定时任务，清理 `expires_at < CURRENT_TIMESTAMP(3)` 的记录）
- `extract_tasks`：超过 30 天且状态为 `completed`/`failed` 的任务可清理
- `orders`：未支付且 `expires_at < CURRENT_TIMESTAMP(3)` 的订单由定时任务自动标记为 `cancelled`

### 9.3 数据库存储方式

数据库中**仅存储相对路径**，不含域名：

```sql
-- questions.content 中引用题干图片

-- questions.options 中引用选项图片
'[{"label": "A", "image_url": "questions/physics/2048/opt_a.png", "is_correct": false}]'

'解析：如下图所示，连接 AC...\n![解析图](questions/math/1024/explain_01.png)'

-- question_groups.material_url 引用材料文件
'materials/chinese/58/content.md'
```

### 9.4 URL 拼接规则

前端/后端通过环境变量配置 CDN 基础路径，运行时拼接完整 URL：

| 环境 | 环境变量 `ASSET_BASE_URL` |
|------|---------------------------|
| 本地开发 | `http://localhost:3000/assets/` |
| 测试环境 | `https://test-cdn.example.com/assets/` |
| 生产环境 | `https://cdn.example.com/assets/` |

**拼接示例**（TypeScript）：
```typescript
const ASSET_BASE_URL = process.env.ASSET_BASE_URL || '/assets/'

function resolveAssetUrl(relativePath: string): string {
  return `${ASSET_BASE_URL}${relativePath}`
}

// 使用
const imageUrl = resolveAssetUrl('questions/math/1024/stem_01.png')
// => https://cdn.example.com/assets/questions/math/1024/stem_01.png
```

**优点**：切换 CDN 或迁移存储只需修改环境变量，无需批量更新数据库记录。

### 9.5 录题流程

```
1. 创建题目/题组，获得 question_id 或 group_id
2. 按目录规范上传素材到对应路径：
   - 单题素材 → /assets/questions/{subject}/{question_id}/
   - 题组材料 → /assets/materials/{subject}/{group_id}/
3. 在 content/options/explanation/material_url 中填写相对路径
4. 保存题目
```

### 9.6 前端渲染逻辑

```typescript
// 伪代码：渲染单题或复合题
async function renderQuestion(q: Question, isFirstInGroup: boolean = false) {
  const resolveUrl = (path: string) => `${ASSET_BASE_URL}${path}`
  
  // 1. 若是题组第一题，先渲染材料
  if (isFirstInGroup || !q.group_id) {
    if (q.material_url) {
      // 长材料：从 URL 加载
      const material = await fetch(resolveUrl(q.material_url)).then(r => r.text())
      render(<MaterialPanel content={material} />)
    } else if (q.material_text) {
      // 短材料：直接渲染
      render(<MaterialPanel content={q.material_text} />)
    }
  }
  
  // 2. 渲染题干（Markdown 渲染器自动处理图片，需配置 baseUrl）
  render(<Markdown baseUrl={ASSET_BASE_URL}>{q.content}</Markdown>)
  
  // 3. 渲染选项
  q.options?.forEach(opt => {
    if (opt.image_url) {
      render(<img src={resolveUrl(opt.image_url)} alt={opt.label} />)
    }
    if (opt.text) {
      render(<Markdown baseUrl={ASSET_BASE_URL}>{opt.text}</Markdown>)
    }
  })
  
  // 4. 渲染解析（答题后展示）
  if (showExplanation && q.explanation) {
    render(<Markdown baseUrl={ASSET_BASE_URL}>{q.explanation}</Markdown>)
  }
}

// 渲染复合题组
async function renderQuestionGroup(groupId: string) {
  const questions = await fetchQuestionsByGroup(groupId) // ORDER BY group_order
  for (let i = 0; i < questions.length; i++) {
    await renderQuestion(questions[i], i === 0)
  }
}
```
